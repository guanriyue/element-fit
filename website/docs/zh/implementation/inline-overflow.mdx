# InlineOverflow 的溢出测量

`InlineOverflow` 需要从当前 DOM 布局中派生一个稳定的单行横向溢出状态。浏览器负责完成字体选择、文本塑形、inline 布局和 ellipsis 绘制，但没有直接暴露一个适用于任意内容的“是否已经绘制省略号”状态。

组件因此组合浏览器提供的两类布局信息：先使用 `scrollWidth` 完成整数尺寸的初步判断；初步结果处于低置信度区间时，再使用 `Range.getBoundingClientRect()` 读取保留小数的内容几何。

## 测量目标

测量过程包含两个对象：

- **可用宽度**：Root 的 content box width。
- **内容宽度**：Content 在当前样式和当前 DOM 结构下形成的单行内容宽度。

组件测量已经参与布局的真实内容，不根据字符数量推算宽度，也不构造隐藏副本。字体、字形、字距和混合 inline 节点都先由浏览器完成布局，再由组件读取结果。

这个模型建立在以下约束上：

- Content 使用横向单行排版。
- Root 的 content box 表达 Content 的目标可用宽度。
- Root 与 Content 分离时，Content 不额外引入 padding、margin 等会改变比较语义的尺寸。

## 第一级：整数尺寸初步判断

Root 与 Content 分离时，组件首先计算：

```ts
const difference = content.scrollWidth - rootContentBoxWidth;
```

Root 与 Content 是同一个元素时，则计算：

```ts
const difference = element.scrollWidth - element.clientWidth;
```

共享元素上的 `scrollWidth` 和 `clientWidth` 都采用 padding box 语义，元素自身的 padding 可以在比较中自然抵消。

[`scrollWidth` 和 `clientWidth`](https://drafts.csswg.org/cssom-view/#extensions-to-the-element-interface) 在 CSSOM View 中以 Web IDL `long` 暴露。浏览器内部可以使用亚像素完成文本布局，但 JavaScript 最终读取到的是整数尺寸。因此，这一级测量是初步判断，不是所有临界位置上的最终结论。

## 低置信度区间

InlineOverflow 当前使用 `1 CSS px` 作为保守的临界区间：

| 初步差值 | 处理 |
| --- | --- |
| `difference >= 1` | 判定为溢出 |
| `difference <= -1` | 判定为未溢出 |
| `-1 < difference < 1` | 使用 Range 继续测量 |

`1px` 用于覆盖整数尺寸可能隐藏的亚像素差异，不表示浏览器的实际误差固定为 `1px`。`0.5px` 或 `0.2px` 在部分浏览器平台上也可能足够；当前值选择了更保守的校正范围。

在常见的单行裁剪布局中，未溢出时 `scrollWidth` 经常刚好等于 `clientWidth`。相等只能说明两个整数尺寸一致，不能排除内容已经在亚像素边界发生裁切，因此差值为 `0` 仍然属于低置信度结果。

Content 不包含子节点时直接判定为未溢出，不创建 Range。

## 第二级：Range 临界校正

初步结果落入低置信度区间时，组件选中 Content 的全部内容，并读取选区的包围矩形：

```ts
const range = content.ownerDocument.createRange();

range.selectNodeContents(content);

const contentWidth = range.getBoundingClientRect().width;
const overflow = contentWidth > availableContentWidth;
```

[`Range.getBoundingClientRect()`](https://drafts.csswg.org/cssom-view/#dom-range-getboundingclientrect) 返回选区中布局片段的包围矩形。返回的 `DOMRect` 保留小数尺寸，使组件能够继续判断整数 `scrollWidth` 无法区分的亚像素差异。

Range 在这里不是通用的文本宽度计算器，也不直接返回 ellipsis 状态。它利用已经完成的浏览器布局，补充当前 DOM 内容的几何信息。CSSWG 的 [issue #4123](https://github.com/w3c/csswg-drafts/issues/4123) 记录了 ellipsis 临界位置缺少可靠检测能力的问题；Range 校正用于降低整数尺寸在这类位置产生的漏判。

## 平台问题与规避方案

整数尺寸造成的临界漏判已经出现在 CSS 标准讨论、浏览器问题跟踪和社区实践中：

- [CSSWG issue #4123](https://github.com/w3c/csswg-drafts/issues/4123) 讨论 ellipsis 已经出现，但 `scrollWidth`、`clientWidth` 或其他几何结果因取整而保持相等的情况。
- [Chromium issue 41468858](https://issues.chromium.org/issues/41468858) 是对应的 Chromium 问题跟踪项。
- [Mozilla bug 1250824](https://bugzilla.mozilla.org/show_bug.cgi?id=1250824) 记录了 `overflow: hidden` 与 `text-overflow: ellipsis` 场景中的 `scrollWidth` 取整问题。
- [Stack Overflow：Wrong ellipsis detection with scrollWidth](https://stackoverflow.com/questions/71440290/wrong-elipsis-detection-with-scrollwidth-when-text-length-is-close-to-width) 展示了临界宽度下的社区复现和通过临时 DOM 副本测量的替代方案。

Range API 是规避这类浏览器尺寸 Bug 的一种解决方案。它不改变浏览器的整数尺寸行为，而是在初步结果置信度不足时，改为读取选中内容带有小数的几何结果。这个方案避免了克隆、挂载和移除临时测量节点，同时仍然建立在浏览器已经完成的真实布局上。

Range 校正不能消除所有浏览器差异，也不代表相关平台问题已经被修复。它绕过的是单纯依赖整数 `scrollWidth` 和 `clientWidth` 的判定路径。

## 保持盒模型一致

Range width 需要与相同语义的可用宽度比较。

### Root 与 Content 分离

组件优先使用 ResizeObserver 提供的 Root content box width。首次尚未取得观测值时，使用 `clientWidth` 减去 inline padding 作为回退：

```ts
const availableContentWidth =
  root.clientWidth - paddingInlineStart - paddingInlineEnd;
```

常规路径和 Range 路径始终与这个 content box width 比较，避免临界校正改变测量基准。

### Root 与 Content 共享元素

常规路径先比较同一元素的 `scrollWidth` 和 `clientWidth`。只有结果进入低置信度区间时，组件才解析 content box width，并将它与 Range width 比较。

这种分层既让常规比较保留 padding box 的对称性，也让 Range 路径使用与选中内容一致的可用空间。

## 为什么只在临界区间使用 Range

当整数差值已经足够明显时，Range 不会改变判断结果。把 Range 限制在临界区间有三个作用：

- 常规场景只读取简单的元素尺寸。
- Range 专注处理整数尺寸信息不足的结果。
- Range 的内容边界不会被扩展成整个组件的通用布局模型。

两级测量的目标不是用 Range 替换 `scrollWidth`，而是根据初步结果的置信度选择浏览器能够提供的下一层几何信息。

## Range 的内容边界

CSSOM View 使用选中的文本片段和顶层元素盒生成 Range 矩形，因此普通文本以及一部分 `inline`、`inline-block`、`inline-flex` 混合内容可以参与校正。

这个几何结果不等于任意 DOM 子树的 intrinsic width：

- margin 和伪元素不属于稳定的选区几何。
- 定位和 transform 可能让视觉范围与单行内容宽度产生不同语义。
- `display: none`、尚未参与布局或不在当前文档中的内容无法得到目标布局尺寸。
- 多行内容会形成多个布局片段，其包围矩形不再表达单行内容宽度。

Range 的特殊文本边界也可能存在浏览器差异。例如 WebKit 的 [issue #296765](https://bugs.webkit.org/show_bug.cgi?id=296765) 记录了换行文本 Range 矩形的问题。该问题不是 InlineOverflow 单行场景的直接复现，但说明 Range 提供的是受具体布局和浏览器实现约束的几何结果。

## 结果与组件边界

Range 校正提高了 ellipsis 临界位置的判断能力，但不把 InlineOverflow 扩展为普遍的 CSS 测量系统。组件仍然只支持当前已渲染的横向单行内容，并要求调用方建立明确、可收缩的 Root 与 Content 布局。
