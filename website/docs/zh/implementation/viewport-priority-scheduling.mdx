# 视窗优先级任务调度

一个测量任务的耗时可能很短，但同一页面中的大量组件会在首屏渲染、容器缩放或样式切换时同时失效。如果所有实例立即读取布局，单个任务的成本会累积成一段连续的主线程工作，使当前帧无法及时完成。

Element Fit 使用视窗优先级调度把任务分为 `near` 和 `far`：

- `near` 表示元素位于视窗或视窗附近，任务进入微任务批次，优先得到结果。
- `far` 表示元素距离视窗较远，任务优先等待浏览器空闲期，并按照有限批次执行。

这是一种削峰策略。它不会减少每个组件最终需要完成的测量，也不会改变测量算法；它把用户更可能看到的工作提前，把远处工作分散到后续执行机会中。

## 采样扩展后的视窗

优先级由元素的 `getBoundingClientRect()` 与扩展视窗相交关系决定：

```ts
const nearViewport =
  rect.bottom >= -verticalMargin &&
  rect.top <= window.innerHeight + verticalMargin &&
  rect.right >= -horizontalMargin &&
  rect.left <= window.innerWidth + horizontalMargin;
```

margin 把 near 范围扩展到实际视窗之外。即将通过滚动进入视窗的元素可以提前完成测量，避免严格使用视窗边界时出现明显的状态延迟。

垂直和水平方向可以分别设置采样范围。margin 是任务优先级的启发式参数，不参与几何判定；调整它只会改变任务何时执行，不应改变最终测量结果。

## 优先级是调度时的样本

`near` 和 `far` 不是元素的持续状态。接近程度在安排任务时采样一次，不使用 IntersectionObserver 持续跟踪可见性，也不因为页面滚动而自动更新。

如果一个 far 元素在任务执行前滚动到视窗附近，但任务没有被重新安排，它仍然保留在 far 队列。far 任务不会被无限暂停，后续空闲批次仍会完成它。再次安排同一个任务时，可以使用新的位置样本把它迁移到 near 队列。

持续可见性跟踪更适合“离屏时不执行”的工作。Element Fit 的目标不同：所有有效测量最终都需要完成，near/far 只用于分散突发负载。为每个实例维护持续观察状态不会改变这项任务的完成条件。

## near 任务在微任务中合并

调度器使用 `Set` 保存 near 任务。当前同步过程第一次加入 near 任务时，只安排一个 microtask；同一轮中继续加入的其他任务复用这次 flush：

```text
schedule A ─┐
schedule B ─┼─→ 一个 microtask → A、B、C
schedule C ─┘
```

flush 开始时会取得当前任务快照，并在执行每个任务前将它从 Set 移除。任务执行期间再次安排自身时，它会进入下一次 microtask，而不会在当前循环中递归执行。

near 队列没有批次数量上限。这样可以尽快得到视窗附近的最终状态，但大量实例同时位于 near 范围时，仍可能形成较长的微任务。优先级调度只能延后 far 工作，不能消除 near 任务自身的脚本、样式计算和布局成本。

## far 任务按空闲预算分批

far 队列优先使用 `requestIdleCallback`。一次 idle callback 按照两个条件限制工作量：

1. 当前批次不超过预设的任务数量上限。
2. 第一项执行后，仅在 `timeRemaining() > 1ms`、或者 callback 已因 timeout 到期时继续执行。

即使浏览器报告的剩余时间为 `0`，每个 callback 也至少执行一个任务。这样可以保证队列持续前进，而不是在页面长期繁忙时反复得到空预算却没有任何进展。

批次上限控制的是一次执行机会中的任务数量，不是时间预算；单项任务过重时，即使批次数量很小，也可能超过一帧可用时间。

far callback 设置有限的 timeout，用于避免浏览器持续繁忙时任务无限饥饿。timeout 到期后，调度器可以忽略空闲时间不足并继续处理当前批次，但仍受任务数量上限限制。timeout 是饥饿兜底，不是任务完成时限，也不是固定延迟。

剩余队列会继续申请下一次 idle callback，直到全部任务完成：

```text
far tasks
  → idle batch 1
  → idle batch 2
  → …
  → empty
```

浏览器不提供 `requestIdleCallback` 时，调度器退回 `requestAnimationFrame`；如果 RAF 也不可用，再退回 timer。回退路径仍然保留批次数量上限，但无法获得真实的空闲时间预算。

## 稳定任务身份用于去重和替换

Set 的 key 是函数身份。重复安排同一个函数引用时，队列中始终只有一项：

```ts
schedule(measure, 'far');
schedule(measure, 'far');
```

第二次调用不会建立第二份待执行工作。任务执行时再读取 store 中的最新节点、尺寸和选项，因此一次执行可以消费等待期间积累的最新状态。

如果每次调度都创建新的闭包，它们具有不同身份，调度器会把它们视为不同任务：

```ts
schedule(() => measure(versionA), 'far');
schedule(() => measure(versionB), 'far');
```

这类代码不能获得自动替换语义。需要“只保留最新请求”时，调用方应提供稳定任务函数，把最新输入保存在 store 中；或者显式取消旧函数后再加入新函数。

稳定身份也支持队列迁移：

- 再次以 `near` 安排 far 任务时，先从 far Set 删除，再加入 near Set。
- 再次以 `far` 安排 near 任务时，先从 near Set 删除，再加入 far Set。
- `cancel(task)` 同时从两个 Set 删除任务。

已经交给浏览器的 microtask、idle callback 或 RAF 不需要同步撤销。它们触发后读取当前 Set；任务已经迁移或取消时，flush 会自然成为空操作。

取消只影响尚未开始的任务。函数已经进入执行过程后，调度器不会中断它；较长的多阶段测量还需要由自己的 token、cleanup 或阶段取消机制保证结果有效。

## 调度器的职责边界

视窗优先级调度只决定任务何时获得执行机会。它不会分析任务内容，也不会自动合并任务内部的 DOM read、DOM write 或状态提交。

任务开始执行后产生多少次样式计算和布局，仍然由任务自身的读写顺序决定。near/far 分类不能替代布局批处理，也不能修复交错读写引起的 forced reflow。

## 位置采样也有成本

`getBoundingClientRect()` 是布局读取。如果此前存在尚未结算的 DOM 或样式写入，位置采样可能要求浏览器同步更新布局。视窗优先级调度降低的是后续大量任务同时执行的峰值，不能让这次读取变成零成本。

因此，位置只在需要安排任务时采样，不在滚动过程中持续读取，也不为了决定优先级读取与位置无关的其他几何信息。

## 错误隔离

每个任务都在独立的 `try/catch` 中执行。一项任务抛出异常时，错误会通过运行环境的错误报告入口重新报告，同一批次中的其他任务仍然继续执行。

错误隔离只保证队列能够继续前进，不会把失败的任务自动重试。任务自身仍然需要负责清理中间状态，并在后续有效信号到来时重新安排工作。

## 能力边界

- 优先级调度不会减少全部测量的总工作量，只改变工作分布。
- near 任务不分片，near 实例过多时仍可能产生长任务。
- far 的执行时机由浏览器负载决定，首次可信状态可能延后。
- 批次任务数量上限不能代替真实时间预算，也不能约束单项任务耗时。
- 优先级在调度时采样，单独滚动不会更新已经排队的任务。
- 位置采样本身是布局读取，需要避免与 DOM 写入交错。
- 只有稳定的函数身份才能获得去重、迁移和取消语义。

视窗优先级调度的核心不是准确预测用户下一步会看到哪个节点，而是把一批同时到来的工作拆成不同紧急程度，让首屏附近的状态先完成，并让远处任务以有限批次继续前进。
