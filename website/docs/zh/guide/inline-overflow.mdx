# InlineOverflow

`InlineOverflow` 用于测量单行内容是否发生横向溢出，并根据派生的 `overflow` 状态组合附属 UI。它不内置 Tooltip、Popover、展开按钮、具体布局或内容裁剪样式。

它适合表格单元格、名称、路径和标签等宽度受限的单行内容。不适合多行截断、纵向书写模式或复杂 transform。

## 能力边界

`InlineOverflow` 只测量 Root 与 Content 当前形成的真实 DOM 布局，不构造隐藏副本，也不模拟尚未渲染的布局。

“反事实测量”指测量当前 DOM 中并不存在的假设状态。例如，Accessory 尚未渲染，但调用方希望提前知道“如果 Accessory 显示并占用一部分宽度，Content 是否会溢出”。这需要临时构造或模拟另一种布局，不属于 `InlineOverflow` 的能力范围。组件先测量现有布局，再根据结果决定 Accessory 是否渲染。


## 测量模型

### 常规测量

Root 与 Content 分离时，组件比较 Content 的 `scrollWidth` 与 Root 扣除 inline padding 后的 content-box width；单元素模式则直接比较同一元素的 `scrollWidth` 和 `clientWidth`。绝大多数情况下，这条路径可以直接得到结果。

CSSOM View 将 `scrollWidth` 和 `clientWidth` 定义为 Web IDL 的 [`long`](https://drafts.csswg.org/cssom-view/#extensions-to-the-element-interface)，因此 JavaScript 最终读取到的是整数。恰好位于 ellipsis 临界像素时，浏览器可能已经绘制省略号，但两个整数仍然相等，普通的 `scrollWidth > clientWidth` 判断会漏掉溢出。CSSWG 的 [issue #4123](https://github.com/w3c/csswg-drafts/issues/4123) 记录了这个平台问题。

### Range 临界修正

当常规测量落在小于 `1px` 的临界区间时，组件会使用 [`Range`](https://developer.mozilla.org/zh-CN/docs/Web/API/Range) 选中 Content 的内容，再通过 [`Range.getBoundingClientRect()`](https://developer.mozilla.org/zh-CN/docs/Web/API/Range/getBoundingClientRect) 获取保留小数精度的包围矩形宽度，并与同一个可用宽度继续比较。

Range 是这里修正常规 overflow 判断误差的核心 API。[CSSOM View](https://drafts.csswg.org/cssom-view/#extensions-to-the-range-interface) 规定，Range 的矩形由选中的文本片段和顶层元素 border area 组成：文本宽度依据字体 advance width 计算，完整选中的顶层元素则贡献自己的 border area。这解释了它为什么适合普通单行文本和一部分混合 inline 内容。

### 浏览器与内容限制

`Range` 和 `Range.getBoundingClientRect()` 已在主流浏览器中广泛可用，但规范只定义 Range 如何汇总几何矩形，并没有规定它必须返回“ellipsis 截断前的 intrinsic width”，也没有定义一个统一的“是否已经绘制省略号”查询。因此，这个 fallback 是基于现有浏览器行为的工程性修正，不保证在所有浏览器和所有 DOM 结构中都能解决临界误判。

Range 几何计算本身也存在浏览器特有的边界问题。例如 WebKit 的 [issue #296765](https://bugs.webkit.org/show_bug.cgi?id=296765) 记录了换行文本 Range 矩形与其他引擎不一致的情况。该问题并非本组件单行场景的直接复现，但说明不能把某一个浏览器中的 Range 结果外推为通用保证。对浏览器覆盖要求较高时，应在目标浏览器中验证实际内容结构，并为完整内容保留 Tooltip 等可访问路径。

## Accessory

Accessory 只根据 `overflow` 状态显示或隐藏，不参与溢出判定。未溢出时，Accessory 不渲染 DOM 节点；溢出后才挂载并进入调用方定义的布局。

一个 Root 可以包含多个 Accessory。Accessory 必须位于对应 Root 的 React context 中，但 DOM 布局位置不需要与 Content 相邻或同行。

## 单元素模式

如果不需要 Root 和 Content 分别渲染两个 DOM 节点，可以让 Root 使用 `asChild`，并将 Content 作为它的唯一 child。Root 的 ref、`data-overflow` 和 Content 的测量 ref 会合并到同一个元素上。

## 布局要点

- Root、Content 和 Accessory 都不提供默认样式。
- 调用方需要为 Root 提供宽度约束，并决定 Content 的单行排版与裁剪策略。
- 文本场景需要为 Content 设置 `white-space: nowrap` 或使用等价方式建立单行排版。如果允许换行，结果不再表示单行内容是否放得下。
- `overflow: hidden`、`overflow: clip`、`text-overflow: ellipsis`、渐变遮罩或仅观测状态都由调用方选择。
- flex 布局通常需要为 Content 设置 `min-width: 0`。
- grid 布局通常需要使用 `minmax(0, 1fr)`，或者为 Content 设置 `min-width: 0`。
- Root padding 会参与测量；组件比较 Content 的 `scrollWidth` 与 Root 扣除 inline padding 后的 content box width。
- Root 与 Content 分离时，不要在 Content 上增加 `padding`、`margin` 等会改变布局计算的样式。这类样式会让“内容宽度”和“目标可用宽度”的关系变得不稳定。单元素模式可以在 Root 与 Content 共享的元素上设置 padding。

## 观测边界

组件使用 ResizeObserver 监听 Root 和 Content 的尺寸变化，并使用 MutationObserver 监听 Content subtree 中的文本和子节点变化。MutationObserver 不观察 attributes；仅修改 class、style、继承样式、已加载字体或伪元素内容时，如果 Root 和 Content 的盒子尺寸都没有变化，组件不保证重新测量。

浏览器目前没有稳定可用的 Computed Style Observer。`font-size`、`font-family`、`letter-spacing` 等 computed style 的变化本身无法被直接观测，因此由这些样式变化导致的 overflow 变化也不保证被捕获。兄弟选择器、父子选择器、主题 class、响应式 class 等间接改变 Content 文本布局的写法都需要谨慎使用；只有等类似 [ComputedStyleObserver](https://github.com/w3c/csswg-drafts/issues/8982) 的能力成熟后，这类变化才可能被更稳定地观测。

首次客户端测量前，内部 overflow 状态为 `false`，`data-overflow` 不存在，Accessory 不渲染。当前不提供 `defaultOverflow`、受控 `overflow` 或手动 remeasure API。
