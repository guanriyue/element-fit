# InlineOverflow

`InlineOverflow` 用于测量单行内容是否发生横向溢出，并根据派生的 `overflow` 状态组合附属 UI。它不内置 Tooltip、Popover、展开按钮、具体布局或内容裁剪样式。

它适合表格单元格、名称、路径和标签等宽度受限的单行内容。不适合多行截断、纵向书写模式、复杂 transform 或需要反事实测量的场景。

## 导入

```tsx
import { InlineOverflow } from '@guanriyue/react-fit/inline-overflow';
```

## 基础用法

Root 和 Content 都不提供默认样式。调用方需要让 Root 形成可测量的盒子，决定 Content 如何获得和收缩宽度，并显式选择单行排版与裁剪方式。

## Accessory

Accessory 只根据 `overflow` 状态显示或隐藏，不参与溢出判定。未溢出时，Accessory 不渲染 DOM 节点；溢出后才挂载并进入调用方定义的布局。

一个 Root 可以包含多个 Accessory。Accessory 必须位于对应 Root 的 React context 中，但 DOM 布局位置不需要与 Content 相邻或同行。

## 单元素模式

如果不需要 Root 和 Content 分别渲染两个 DOM 节点，可以让 Root 使用 `asChild`，并将 Content 作为它的唯一 child。Root 的 ref、`data-overflow` 和 Content 的测量 ref 会合并到同一个元素上。

## Ellipsis 边界校正

在 ellipsis 的临界位置，浏览器可能已经绘制省略号，但 JavaScript 读取到的 `clientWidth` 和 `scrollWidth` 仍然相等。此时使用 `scrollWidth > clientWidth` 的普通判断会得到“未溢出”，从而漏掉已经出现的省略。这个浏览器平台问题可以参考 CSSWG 的 [issue #4123](https://github.com/w3c/csswg-drafts/issues/4123)。

组件会对这类边界情况做额外校正。下面两组内容、布局和宽度完全一致，用于对比“启用边界校正”和“关闭边界校正”时的判定差异。校正使用 Content 的 Range bounding rect 补充整数精度的 `scrollWidth`；它适合普通单行 flow，但不等价于任意 DOM 子树的 intrinsic width。

## 布局要点

- Root、Content 和 Accessory 都不提供默认样式。
- 调用方需要为 Root 提供宽度约束，并决定 Content 的单行排版与裁剪策略。
- 文本场景需要为 Content 设置 `white-space: nowrap` 或使用等价方式建立单行排版。如果允许换行，结果不再表示单行内容是否放得下。
- `overflow: hidden`、`overflow: clip`、`text-overflow: ellipsis`、渐变遮罩或仅观测状态都由调用方选择。
- flex 布局通常需要为 Content 设置 `min-width: 0`。
- grid 布局通常需要使用 `minmax(0, 1fr)`，或者为 Content 设置 `min-width: 0`。
- Root padding 会参与测量；组件比较 Content 的 `scrollWidth` 与 Root 扣除 inline padding 后的 content box width。
- Root 与 Content 分离时，不要在 Content 上增加 `padding`、`margin` 等会改变布局计算的样式。这类样式会让“内容宽度”和“目标可用宽度”的关系变得不稳定。单元素模式可以在 Root 与 Content 共享的元素上设置 padding。

## 观测边界

组件使用 ResizeObserver 监听 Root 和 Content 的尺寸变化，并使用 MutationObserver 监听 Content subtree 中的文本和子节点变化。MutationObserver 不观察 attributes；仅修改 class、style、继承样式、已加载字体或伪元素内容时，如果 Root 和 Content 的盒子尺寸都没有变化，组件不保证重新测量。

浏览器目前没有稳定可用的 Computed Style Observer。`font-size`、`font-family`、`letter-spacing` 等 computed style 的变化本身无法被直接观测，因此由这些样式变化导致的 overflow 变化也不保证被捕获。兄弟选择器、父子选择器、主题 class、响应式 class 等间接改变 Content 文本布局的写法都需要谨慎使用；只有等类似 [ComputedStyleObserver](https://github.com/w3c/csswg-drafts/issues/8982) 的能力成熟后，这类变化才可能被更稳定地观测。

首次客户端测量前，内部 overflow 状态为 `false`，`data-overflow` 不存在，Accessory 不渲染。当前不提供 `defaultOverflow`、受控 `overflow` 或手动 remeasure API。

这里的“反事实测量”指测量一个当前 DOM 布局里并不存在的假设状态。例如：Accessory 还没有渲染，但调用方想提前知道“如果 Accessory 显示并占掉一部分宽度，Content 会不会溢出”。这需要临时构造或模拟另一种布局再测量。`InlineOverflow` 不处理这种模式，它只测量当前 Root 与 Content 形成的真实布局，再根据结果决定 Accessory 是否渲染。

在极限临界范围内，浏览器可能已经绘制 ellipsis，但 JavaScript 读取到的尺寸仍不足以表达同等精度。组件会在 `scrollWidth` 与 Root content-box width 相差小于 `1px` 时尝试 Range 边界校正。Range 能覆盖普通单行 flow 中的文本、元素和混合内容，但 margin、伪元素、定位、transform 和多行布局仍不属于可靠测量范围。
